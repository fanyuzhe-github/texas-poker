## Deno Deploy EA 首次部署踩坑（01:1x）

用户截图：新版控制台（console.deno.com）里 app `texas-poker` 显示 **Not deployed yet**，
Recent Production Builds 里 `eb15edf` 是**红色失败**。问「点哪里呀」。

**根因**：新版 Deploy 会按仓库内容自动猜测构建命令。仓库根有 `package.json`（Vue 前端）
→ 它去跑 npm install / npm run build，而这跟后端毫无关系（前端早就托管在 GitHub Pages 了）。

**修法**：根目录新增 `deno.json`，用源码配置压过面板自动配置：
```json
{ "unstable": ["kv"], "deploy": { "runtime": { "type": "dynamic", "entrypoint": "./server/main.ts" } } }
```
不写 `deploy.install` / `deploy.build` → 不跑任何安装构建命令，直接把 main.ts 当入口。

**顺带发现的两个硬门槛**：
1. ⚠️ 新版 Deploy 的 KV **必须手动 Provision 再 Assign 给 app**，`Deno.openKv()` 不会自动建库
   （官方 Databases 文档明确写 "not automatically provision"）→ 不分配则部署成功但运行时挂
2. ⚠️ `--unstable-kv` **不能传给 Deploy 运行时**（参数固定）→ 必须靠 `deno.json` 的 `"unstable": ["kv"]`
   本地冒烟时先漏了这个，`Deno.openKv is not a function`，加上后 ping / 空房间读取都正常

**验证**：`deno check` 通过；本地 `deno run -A server/main.ts` 无 flag 启动，
`/api/ping` 返回 `{"ok":true,...}`、空房间返回 `{"ok":true,"snapshot":null}`。

已推送 `deb2457`，触发新一轮构建。

## 修「A 改的 B 收不到」（02:0x，commit `87351cf`）

用户报：**A 电脑改数据同步不到 B，B 改的能同步到 A** —— 单向。

**排查顺序（先证伪后端，别一上来就改前端）**：
1. 两条 curl SSE 并发连同一房间 → 一次 POST 两边都收到 → **后端 kv.watch 广播没问题**
2. 浏览器当 A 改底注 → 线上确实变成 35/55 → **A 的推送是通的**
3. 剩下只有 B 那条 SSE 链路 → 定位到**假死**

**根因**：休眠唤醒 / 切 WiFi / 代理掐空闲连接后，SSE 连接进入「开着但收不到东西」的状态，
EventSource 不触发 onerror（TCP 没被 RST/FIN），前端完全无感。
- B→A 通：POST 是主动请求，与那条死连接无关
- A→B 不通：只能靠 B 的死 SSE，收不到

**三处修改**：
- `server/main.ts`：心跳 `: ping`（25s）→ `event: ping`（20s）。
  ⚠️ 关键：注释行不触发任何 JS 事件，前端收不到，等于没有心跳
- `src/utils/live.js`：加假死看门狗（15s 检查 / 70s 静默重连），返回值上挂 `reconnect`；
  加 `onStatus` 回调上报 live/down/connecting
- `GameDetail.vue`：
  - `startLiveWatch` 接 `onStatus`；新加 `pullLiveSnapshot`（主动补拉）与 `handleLiveWake`
  - created/beforeDestroy 挂 `visibilitychange` + `online`
  - `scheduleLivePush` 抑制判断改用 `liveLastPushAt`（**不能用 liveLastSyncAt**，收云端也刷新它）
    ⚠️ 且抑制时改成延后 2 秒再推，不再直接丢弃
  - 设置页显示连接状态

**验证**（本地新版 deno + dist 静态服务 + 真浏览器）：
- A 连上后 `link:"live"`，启动时被云端覆盖成种子数据 ✓
- A 改底注 10→77 → B 的 SSE 收到 77 ✓
- **把 A 的基线重置为 0 后触发 reconnect → 4 秒内自动补上 base 88、「另一台加的」** ✓
  （这条是修复的核心：重连瞬间服务端推当前 state，落后的自动跟上）
- 本地 26 秒 SSE 收到 1 次 `event: ping` ✓
- 单测：`test-live.js` 24 → **43 项**（假 EventSource 覆盖 ready/ping/脏 JSON/别的应用数据/
  重连关旧开新/重连后状态回 live/无 EventSource 不炸）；全量 20 个文件全绿

## 同步服务被停服 + 改短轮询（10:36，commit `a7821dc`）

用户截图：设置页弹「连不上同步服务，检查地址与网络」。

**真因不是网络**：`curl /api/ping` 返回
`503 Service Unavailable (USAGE_EXCEEDED) — This application is suspended due to usage limits being exceeded.`
整个 app 所有路径都 503。503 响应**没有 CORS 头** → 浏览器 fetch 抛 TypeError → 前端只能报「连不上」，
所以用户看到的是网络类文案，实际是账号额度爆了。

**为什么会爆**：Deno 免费层按 **768MB × 每秒** 计内存时间（Free 150 GiB·hr/月，
「未验证组织」额度更低）。SSE 长连接让实例一直处于 loaded 状态、无法缩容到 0：
一台设备挂一夜 ≈ 0.75 GB × 24h = 18 GiB·hr/天。两三台设备 + 我的 E2E 测试 → 十几小时就烧穿。
昨晚 01:00 上线，今早 10:30 停服，量级对得上。

**修法（架构级）**：
- 服务端 `/api/state?since=`：新增 `["meta", room]` 小键存 `{updatedAt,size}`，POST 时一并写；
  since 不落后时只回 `{"ok":true,"unchanged":true,"updatedAt":N}`（45 字节，实测），不下发整份快照
- 前端 `pollState()` + `pollLiveOnce()`：10 秒一轮、页面隐藏即暂停、失败退避 10/20/40/60s
- 删掉 `subscribeState` 的调用（函数保留，注释标「已弃用」；server /api/watch 也留着但不用）
- ⚠️ 顺手修了个真 bug：`request()` 原来先 `res.json()` 再判状态码，停服返回纯文本 → 走进
  「服务返回了看不懂的内容」。改成先按状态码判（404/503/5xx），再解析

**验证**（本地 deno + dist 静态服务 + agent-browser + curl 当第二台设备）：
- 接口：空房间 `snapshot:null` / since=5000 → 45B unchanged / since=4000 → 完整快照 /
  更旧写入 409 / 新写入后 since 能拿到新版
- 启动拉取：注入旧数据打开页面 → 变成「云端甲」、`status:"live"`
- 反向：curl 推「另一台的乙」→ 12 秒内页面跟上（base 20）
- 正向：页面改底注 20→66 保存 → 线上立刻变 66，`liveLastPushAt` 有值
- 断线：停服务 14s → `status:"down"`「连不上同步服务，正在重试（改动仍保存在本机）」
- 自愈：重启服务 → 10 秒内回到 `live`
- 单测 `test-live.js` 43 → **54 项**（新增 pollState 11 项：since 参数、unchanged、快照解析、503 文案、网络异常文案）
